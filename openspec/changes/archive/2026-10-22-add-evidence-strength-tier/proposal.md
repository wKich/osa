# Proposal

## Why

A feature row's `verified` status names a test, and `bridge/test/crosscheck.test.ts`
proves that test exists — but nothing records whether the fixture that test
asserts against was captured from a real run or authored from a reading of the
pinned source. Two rows rest on authored fixtures that can only ever agree with
themselves: `maki-subagent.jsonl` (shapes source-pinned from `sdk_mode.rs`
v0.6.4, "never captured from a live subagent turn" per the comment in
`bridge/test/golden.test.ts:40`) and `maki-stream.jsonl` (`stream_event`
envelope spelling "sdk_mode-string-derived, never captured from a live
streaming provider", `golden.test.ts:31`). Their goldens are generated by
projecting those same fixtures, so the pair is self-consistent by construction
and no future run can contradict it.

The report cannot express this. Both rows print as plain `verified`, which
overstates them: `subagent-nesting` is verified for the *translation* the
bridge performs, not for the *wire shape* it was handed. `maki-stream.jsonl` at
least earned a `degraded` status and a `shortcut:` comment in `translator.ts`;
`subagent-nesting` has neither, and `crosscheck.test.ts` has no way to notice.

## What Changes

- Record fixture provenance once, in a committed machine-readable file, for the
  two authored fixtures and every fixture added later: whether it was captured
  live or authored from the pin, and where the shape came from.
- Enforce the file against the fixtures on disk in `crosscheck.test.ts`, so a
  fixture added without provenance fails the suite rather than silently
  defaulting to the stronger claim.
- Teach `gen-compat.ts` to render a provenance note on any feature row whose
  evidence chain reaches an authored fixture, so the report distinguishes
  "a live run proves this" from "a test pins our reading of the pin".
- Extend `running-feature-discovery` and `proposing-coverage-change` by two
  lines each, so a newly recorded row carries its provenance and a coverage
  change that adds a fixture declares what kind it is.
- Tag `subagent-nesting` with the `contract-only` caveat its own fixture
  comment already states in prose, so the report says what the code comment
  says.

No status flips. No bridge behavior changes. `subagent-nesting` stays
`verified` — the golden genuinely proves the translation — and the caveat
narrowly scopes what that word is claimed to cover.

## Capabilities

### New Capabilities

(none — this change adds provenance to existing evidence; it introduces no new
observable bridge behavior)

### Modified Capabilities

- `opencode-tui-bridge`: the "Generated compatibility report" requirement
  carries evidence provenance on feature rows, and the "Defect inventory and
  discovery loop" requirement records fixture provenance when a discovery pass
  adds a fixture.

## Impact

- `bridge/test/fixtures/provenance.json` — new file, two entries.
- `bridge/test/crosscheck.test.ts` — one new assertion; existing assertions
  untouched.
- `scripts/gen-compat.ts` — renders the provenance note; `make compat`
  regenerates `docs/compatibility.md`.
- `bridge/compat/statuses.json` — the `subagent-nesting` row gains a
  `contract-only` caveat field. No other row changes status.
- `.opencode/skills/running-feature-discovery/SKILL.md`,
  `.opencode/skills/proposing-coverage-change/SKILL.md` — two lines each.
- Unaffected: `bridge/src/**`, the golden fixtures, the `make test` stub suite,
  and every security invariant in `AGENTS.md`. This change reads and records
  provenance; it adds no network, mount, env, or egress surface.
