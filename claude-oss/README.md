# claude-oss

Run [Claude Code](https://code.claude.com/docs/en/overview) natively inside an
NVIDIA OpenShell sandbox, with the same isolation as the Maki and OpenCode
paths in this repository:

- a pinned, agent-only image;
- credentials only from OpenShell provider profiles;
- egress denied by default;
- files moved only by explicit upload and download.

Both a per-call Anthropic API key and a Claude Pro/Max subscription token
(from `claude setup-token` on the host) work. Neither one ever enters the
sandbox, and Claude Code never logs in there.

The `claude-oss` helper (`bin/claude-oss`) does every step for you, the way
`maki-oss` does for Maki. [Without the helper](#without-the-helper) lists the
plain `docker` and `openshell` commands it runs.

| Path | What it is |
|---|---|
| `image/Dockerfile` | Base image `claude-agent:local`: pinned native Claude Code, uid/gid 1500, no Node/Bun, no MCP, no plugins, no login state |
| `image/managed-settings.json` | Root-owned `/etc/claude-code/managed-settings.json`: deny rules that hold in every permission mode, and switches that stop nonessential traffic |
| `image/claude.json` | First-run seed for `/sandbox/.claude.json`: onboarding done, `/sandbox/project` trusted |
| `image/approve-api-key` | Root-owned launcher step: approves the attached API key placeholder before the TUI starts |
| `providers/claude-anthropic.yaml` | `ANTHROPIC_API_KEY` as `x-api-key` to `api.anthropic.com`, bound to `/usr/local/bin/claude` |
| `providers/claude-anthropic-oauth.yaml` | `CLAUDE_CODE_OAUTH_TOKEN` as a bearer token to `api.anthropic.com`, bound to `/usr/local/bin/claude` |
| `providers/catalog.tsv` | Profile → credential env var, example model |
| `providers/stores.tsv` | Stored-credential slug (Maki or OpenCode store) → profile, for `claude-oss provider setup` |
| `providers/template.yaml` | Inert profile template for custom providers generated by `provider setup` |
| `policies/minimal.yaml` | Sandbox policy: filesystem floor, hard Landlock, uid/gid 1500, no egress of its own |

The security invariants in [`AGENTS.md`](../AGENTS.md) apply unchanged. In
particular:

- Never pass a credential through `--env`/`--env-from`.
- Never log in inside a sandbox (`/login`, `claude auth`, `claude setup-token`).
- Never set `ANTHROPIC_BASE_URL` or an `apiKeyHelper` there.
- Never mount or upload `~/.claude`, `~/.claude.json`, or `~/.config/anthropic`.
- Never write the provider placeholder prefix into a file the agent can read.

## Quick start with the helper

From the repository root (or with its `bin/` on `PATH`):

```sh
bin/claude-oss image build                     # claude-agent:local

# Subscription (Claude Pro/Max): create the token on the host
claude setup-token
export CLAUDE_CODE_OAUTH_TOKEN=…
bin/claude-oss provider setup --env CLAUDE_CODE_OAUTH_TOKEN --yes

# …or a per-call API key
bin/claude-oss provider setup --from maki --credential anthropic --yes
```

`provider setup` records the provider in `~/.config/claude-oss/config.toml`,
and each new project sandbox attaches it. To use a provider you created
yourself, set `providers = "claude-anthropic-oauth"` in that file, or export
`CLAUDE_OSS_PROVIDERS` (see
[Choosing the credential](../docs/ai/reference/claude.md#credentials)). Attach only
one of the two to a sandbox: when both are attached, Claude Code uses the API
key, and `claude-oss doctor` warns.

Then, from any project directory:

```sh
claude-oss                                     # TUI, no first-run screens
claude-oss run "reply OK"                      # headless; prints stream-json events
claude-oss run --resume <session_id> "and now?"
claude-oss status
claude-oss rm --yes
```

The first session creates the project's sandbox (`cc-<directory>-<hash>`),
uploads the project, and attaches the remembered provider. On exit, the
helper collects the sandbox changes as a patch and applies it only when the
sandbox baseline still matches the host. See
[docs/ai/reference/claude.md](../docs/ai/reference/claude.md) for configuration
and the differences from `maki-oss`, and
[docs/ai/playbooks/claude.md](../docs/ai/playbooks/claude.md) for the ordered
sandbox path.

## Without the helper

### Build the image

```sh
docker build -t claude-agent:local claude-oss/image
docker run --rm claude-agent:local claude --version   # 2.1.308 (Claude Code)
```

The Dockerfile downloads
`https://downloads.claude.ai/claude-code-releases/<version>/linux-<arch>/claude`,
checks it against the pinned SHA-256, and installs it at
`/usr/local/bin/claude`. To bump the version, change `CLAUDE_VERSION` and both
`CLAUDE_SHA256_*` args together. Read the checksums from the signed release
manifest:

```sh
V=2.1.308
curl -fsSL https://downloads.claude.ai/claude-code-releases/$V/manifest.json \
  | jq -r '.platforms["linux-arm64"].checksum, .platforms["linux-x64"].checksum'
```

The manifest has a detached signature (`manifest.json.sig`) and a published
signing key. See
[Claude Code setup](https://code.claude.com/docs/en/setup#binary-integrity-and-code-signing).
After a bump, rerun the verification below. The first-run seed and the API
key approval rely on `.claude.json` keys that the official docs do not
describe.

### Load a provider profile

```sh
openshell profile lint --from claude-oss/providers
openshell profile import -f claude-oss/providers/claude-anthropic-oauth.yaml --global

# From your host environment (the token never enters the sandbox):
CLAUDE_CODE_OAUTH_TOKEN=<token> openshell provider create \
  --name claude-anthropic-oauth --type claude-anthropic-oauth --from-existing
```

For an API key, use `claude-anthropic.yaml`, `ANTHROPIC_API_KEY`, and the
name `claude-anthropic`.

### Create a sandbox

```sh
openshell sandbox create --name claude \
  --from claude-agent:local \
  --policy claude-oss/policies/minimal.yaml \
  --provider claude-anthropic-oauth \
  --upload ./my-project:/sandbox/project
```

`--upload ./my-project:/sandbox/project` lands the directory at
`/sandbox/project/my-project`. The seed trusts `/sandbox/project`, so a
deeper working directory asks for trust once.

### Run Claude Code

**Headless.** Redirect stdin from `/dev/null`, because `sandbox exec` leaves
it open.

```sh
openshell sandbox exec -n claude --workdir /sandbox/project/my-project --no-login-shell -- \
  claude -p --output-format stream-json --verbose --dangerously-skip-permissions \
  --model sonnet "reply OK" </dev/null

# Continue a run by its session_id (from the last event):
openshell sandbox exec -n claude --workdir /sandbox/project/my-project --no-login-shell -- \
  claude -p --output-format stream-json --verbose --dangerously-skip-permissions \
  --resume <session_id> "and now?" </dev/null
```

**Interactive TUI.** With an API key attached, run the approval step first.
Otherwise Claude Code asks whether to use the key, and its default answer
(No) disables it.

```sh
openshell sandbox exec -n claude --tty --workdir /sandbox/project/my-project --no-login-shell -- \
  sh -c '/usr/local/libexec/claude-oss/approve-api-key; exec "$@"' sh \
  claude --dangerously-skip-permissions
```

Always use Claude Code's default config locations in the sandbox
(`/sandbox/.claude/` and `/sandbox/.claude.json`). `sandbox exec` does not
pass image `ENV` through, so a `CLAUDE_CONFIG_DIR` set in the image never
reaches the agent.

### Bring files back

```sh
openshell sandbox download claude /sandbox/project/my-project/<file-or-dir> ./out/
```

### Tear down

```sh
openshell sandbox delete claude
```
