# Design

## Context

`verified` means "a test proves it", and `crosscheck.test.ts:46` enforces that
the named evidence resolves to a test or fixture under `bridge/test/`. That
check is purely structural — it cannot see what the fixture is *made of*. Two
fixtures were authored rather than captured:

- `bridge/test/fixtures/maki-subagent.jsonl` — the `parent_tool_use_id`
  frames' shape is source-pinned from `sdk_mode.rs` v0.6.4. Comment at
  `bridge/test/golden.test.ts:40-45`: "never captured from a live subagent
  turn".
- `bridge/test/fixtures/maki-stream.jsonl` — the `stream_event` envelope
  spelling is sdk_mode-string-derived. Comment at `golden.test.ts:31-33`,
  with a matching `shortcut:` note in `bridge/src/translator.ts`.

The other five fixtures are byte-identical copies of real captures committed
under `openspec/changes/archive/2026-10-21-add-opencode-tui-bridge/evidence/`
(`maki-plain`, `maki-tool`, `maki-precheck`, `maki-permission` verified
identical; `maki-retry` is a copy of a real capture with one `api_retry` frame
spliced in).

Because a golden is generated by projecting its own fixture, an authored
fixture and its golden agree no matter what upstream does. That is the
circularity this change makes visible instead of trying to eliminate — the
elimination is the live-capture follow-on, not this one.

See proposal.md for why; this document is only how to record and enforce it.

## Goals / Non-Goals

**Goals:**

- Provenance is recorded once, in one file, not scattered across comments.
- A fixture added without provenance fails the suite — the default must not be
  the stronger claim.
- The report tells a reader which `verified` rows rest on authored wire shapes.
- The loop records provenance for fixtures it adds in future iterations.

**Non-Goals:**

- Capturing a live subagent or streaming turn. That is the third follow-on
  change, and its scope is set by this one's file existing.
- Flipping any status. `subagent-nesting` genuinely proves the translation.
- Tiering route rows. The 128 `served-faked` rows cite `bridge/src/`, where
  provenance is the source file itself; there is no fixture to describe.
- Reviewing the other seven fixtures for hidden authorship. The audit that
  produced this change compared each against its archived origin; a future
  audit belongs to whoever adds a fixture.

## Decisions

### D1 — Provenance lives in a fixture-indexed JSON file, not in the fixtures

`bridge/test/fixtures/provenance.json`, keyed by fixture filename:

```json
{
  "maki-subagent.jsonl": {
    "kind": "authored",
    "derivedFrom": "tontinton/maki src/sdk_mode.rs @ v0.6.4 (parent_tool_use_id on assistant/user frames)",
    "note": "never captured from a live subagent turn"
  },
  "maki-retry.jsonl": {
    "kind": "mixed",
    "derivedFrom": "copy of maki-plain.jsonl with one system/api_retry frame spliced in",
    "note": "the spliced frame is source-derived; the surrounding turn is captured"
  }
}
```

`kind` is `captured` | `authored` | `mixed`. An unlisted fixture defaults to
**nothing** — D2 makes unlisted a failure, so the default cannot be read as
`captured`.

**Alternative considered:** a `provenance` header line at the top of each
fixture. Rejected — the fixtures are `.jsonl` streams that `runFixture` parses
line by line, and a header line would need a skip rule in every reader
(`golden.test.ts`, `discovery.ts`, `api-check.ts`) to avoid corrupting the
projection. A sibling file costs nothing.

**Alternative considered:** deriving provenance from git history (`git log
--diff-filter=A`). Rejected — it answers "when was this committed", not "was
the wire shape observed", and it cannot distinguish `maki-retry.jsonl`'s
spliced frame from its captured surroundings. It also makes the test suite
depend on git metadata being present, which the offline gate cannot assume.

### D2 — `crosscheck.test.ts` fails a fixture with no provenance entry

New assertion, alongside the existing five:

- every file in `bridge/test/fixtures/` has an entry in `provenance.json`
- every entry names a fixture that exists
- every entry's `kind` is one of the three values

This is the enforcement half. Without it the file rots the moment the next
fixture lands.

### D3 — The report renders provenance, and does not change any status

`gen-compat.ts` reads `provenance.json` and, for a feature row whose evidence
is a test that consumes an authored or mixed fixture, appends the provenance
note to the row's Evidence cell. `verified` stays `verified`; the note narrows
what it is claimed to cover.

`subagent-nesting` additionally gains a `caveat: "contract-only"` field in
`statuses.json`, which the report renders. That is the vocabulary the discovery
skill already defines — "claim coverage of a route the TUI never called
without saying *contract-only*" — extended to a feature whose wire shape was
never called at all. The skill's own rule puts the caveat in the evidence
matrix coverage column rather than in `statuses.json`; this design puts it in
`statuses.json` because `gen-compat.ts` renders from that file and nowhere
else, and a caveat only a human remembers to mention is not a caveat.

**Alternative considered:** a new status value (`verified-contract-only`).
Rejected — it would need a change to the enforced `FEATURE_STATUS` vocabulary
and to the `opencode-tui-bridge` requirement listing the four statuses, for a
distinction that two rows express and that a note expresses without widening
the vocabulary.

### D4 — Provenance is a note, and only where the chain reaches an authored fixture

The report stays a three-lens document. Provenance attaches to the Evidence
cell of the affected rows rather than becoming a fourth lens: it is a property
of evidence, not a property of a feature.

### D5 — Two skill edits, two lines each

- `running-feature-discovery`, in "Record findings": a newly added feature row
  whose fixture is authored or mixed gets a `provenance.json` entry in the
  same change.
- `proposing-coverage-change`, in the tasks list: a coverage change that adds
  a fixture states its kind and adds the entry.

Both are git-tracked, so the edits are reviewable diffs alongside the file they
protect.

## Risks / Trade-offs

- **[The provenance file drifts from the fixtures]** → D2 makes the suite fail
  in both directions: a fixture with no entry, and an entry for a fixture that
  is gone.
- **[`mixed` becomes a dumping ground for "mostly captured"]** → The file
  carries a `derivedFrom` string per entry, so a reader sees exactly which
  part was spliced rather than a bare label. `maki-retry.jsonl` is the only
  current instance and it is spelled out.
- **[A note is weaker than a status, and a reader skims past it]** → Accepted:
  the alternative was widening the status vocabulary for two rows (D3). The
  note sits in the Evidence cell the reader is already looking at to find the
  test.
- **[The live-capture follow-on makes some entries obsolete]** → Expected and
  harmless: a fixture replaced by a real capture gets its entry flipped to
  `captured`, which is exactly the signal that the circularity is broken.
- **[Provenance is self-reported and therefore only as good as the author]** →
  Inherent. The check that cannot be self-reported — a live capture contradicting
  the authored shape — is the follow-on change's job.

## Migration Plan

One commit: the provenance file, the `crosscheck` assertion, the `gen-compat`
rendering, the one `statuses.json` caveat field, and the two skill edits. The
suite gates it — if the new assertion fails, the file is incomplete, and the
fix is to add the missing entry rather than to relax the assertion. Rollback is
a revert; nothing reads the new file except the test and the report generator.

## Open Questions

None that change the specs, the approach, or the task breakdown. Whether the
authored wire shapes turn out to be *wrong* is answerable only by the
live-capture follow-on, and is the entire reason that change exists.
